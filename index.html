IP页滑动热区重定义 · 手势引导设计

这个需求让我第一次意识到：没有问题的方案，可能才是最大的问题。
问题是如何发现的
数据信号

需求方在复盘 IP 页数据时注意到两件事并列出现：左右滑动的 Tab 使用率持续走低，而 IP 详情页的曝光量一直上不去。两条数据本来是独立的，但放在一起看，指向同一个问题：用户每天产生大量左右滑动行为，这些手势全部消耗在了 Tab 上，而 IP 详情页几乎没有一个顺手的入口。

核心观察

IP 页的左右滑动热区，本质上是一块"被占用但没有被好好使用"的资源。Tab 设计本身没有体验问题，这也是它一直没被质疑的原因——没有投诉，没有负向反馈，但也没有在创造什么价值。

卡点与难点
打破已有手势预期的风险

用户对"左右滑 = 切 Tab"已经形成了稳定预期。把同一个手势重新映射到完全不同的行为，短期内一定会产生迷失感——用户滑了一下，发现页面变了，不知道怎么回去，也不确定自己是不是误触了。这个认知断层如果处理不好，比不改更糟。

引导的尺度边界

解决认知断层的方式是引导，但引导本身也有成本。做得太重，每次进入都弹提示，用户会觉得被打扰；做得太轻，用户根本没注意到，功能发现率依然很低。难点在于：这个引导只有一次机会，必须在第一次触发时就让用户真正理解。

为什么会出现这个问题

Tab 在产品早期是有价值的——当内容模块多、切换频繁时，左右滑是合理的导航方式。但随着 IP 页内容结构调整，Tab 数量缩减，内容密度下降，这个设计的前提已经不成立了，但交互层没有随之迭代。

更深层的原因是：设计评审不容易质疑"没有问题"的东西。 有 bug 会被修，有投诉会被改，但一个"用起来还行、只是没什么用"的设计，很容易在每一轮评审中都被放过。这个需求是少数几个主动去挖这类问题的案例。

决策过程与原因
先评估原方案的实际价值

在决定改之前，先确认 Tab 本身是否值得保留。结论是：Tab 内容少、使用率低，去掉不会造成功能损失，用户也不会因为少了 Tab 而困惑——他们本来就没在用它。这给了改动足够的底气。

方案对比

备选方案 A 是保留 Tab 滑动不变，另在页面其他位置增加 IP 入口。风险低，但需要占用新的布局空间，且新入口的发现率很难保证。

方案 B 是直接将左右滑重新定义为切换 IP 页，复用现有手势习惯，不需要教用户新手势，只需要更新他们对"滑动触发什么"的认知。代价是短期的认知摩擦，但可以通过引导设计来承接。

最终选择方案 B 的原因

方案 B 的入口效率更高——直接复用用户的高频手势，不新增学习成本。而认知摩擦的问题，只要引导设计做对，只需要一次。我的判断是：用户只要完成一次正确的手势，心智模型就更新了，之后不再需要提示。 所以引导的策略是：进入页面时出现一次动效暗示，随用户完成手势后消失，不重复出现。
